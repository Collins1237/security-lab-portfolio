## Objective

Assess a web application for the most common classes of vulnerability (the OWASP Top 10), demonstrate the risk of each, and — the half that actually gets paid for — document how to remediate them. Target: a locally-deployed, deliberately-vulnerable application (OWASP Juice Shop) running on a host I own.


## Tools & target

- `docker` — deploy the vulnerable target in an isolated container
- OWASP Juice Shop — intentionally-vulnerable web app (safe, legal practice target)
- A web browser + its built-in developer tools — the core web-testing toolkit

## Findings — Injection & XSS

**Injection (A03).** User-supplied input is incorporated into interpreter commands (e.g. SQL) without separation of code and data, allowing the input to alter query logic. **Remediation:** use parameterized queries / prepared statements and least-privilege database accounts; never concatenate untrusted input into a query.

**Cross-Site Scripting (part of A03).** Untrusted input is rendered back into pages without context-aware encoding, letting attacker-controlled script execute in victims' browsers. **Remediation:** context-aware output encoding, a restrictive Content-Security-Policy, and framework auto-escaping; validate input but rely on output encoding for the fix.


## Findings — Access Control & Misconfiguration

**Broken Access Control (A01).** Authorization is not consistently enforced server-side; manipulating identifiers or calling endpoints directly can expose other users' data or privileged functions. **Remediation:** enforce access checks on the server for every request, deny by default, and test for horizontal/vertical privilege escalation.

**Security Misconfiguration (A05) & Sensitive Data Exposure.** Leftover interfaces, default credentials, verbose error messages, and confidential files in web-accessible paths widen the attack surface. **Remediation:** remove unused features/accounts, return generic error pages, store secrets and documents outside web roots, and review configuration as part of deployment.


## Methodology

The application was deployed locally in Docker and assessed through the browser and its developer tools. Testing focused on the OWASP Top 10 categories above; the application's built-in Score Board was used to confirm which vulnerability classes were successfully demonstrated. All testing was confined to the locally-owned instance.


## Remediation summary

- Separate code from data everywhere: parameterized queries, output encoding, a Content-Security-Policy.
- Enforce authorization server-side on every request; deny by default.
- Harden configuration: no defaults, no debug interfaces, generic errors, secrets out of web roots.
- Keep dependencies patched and validate all input — but fix injection/XSS at the OUTPUT boundary.

## What I learned (Security+ / pentest concepts)

- The OWASP Top 10 as a shared vocabulary for web risk, led today by Broken Access Control and Injection.
- Injection and XSS both stem from mixing untrusted input with code; the fix is separation, not blocklists.
- A finding is only useful with a remediation — report-writing is the core deliverable of a penetration test.
- Running the target in Docker on a host I own keeps the whole exercise authorized and isolated.
